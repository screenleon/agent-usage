# Gate override context: fix/windows-local-tests

## qa-tester-F001 (cmd/agent-usage/console_windows.go, enableConsoleANSI)

qa-tester correctly notes that `enableConsoleANSI`'s real Win32 call chain
(`GetStdHandle`/`GetConsoleMode`/`SetConsoleMode` via `kernel32Console` in
`console_windows.go`) has never been exercised on an actual Windows host —
only the injected-fake decision logic in `console_test.go` runs in CI.

This repository's GitHub Actions usage is on the free tier, which does not
include Windows/macOS runner minutes for this account, so a `windows-latest`
CI job is not available right now. Adding native Windows CI is out of scope
for this change.

Given that constraint, the maximum feasible automated coverage for this PR
is: (1) `enableConsoleANSIWith`'s branch logic fully unit-tested against an
injected `consoleAPI` fake (`console_test.go`), covering redirected writer,
failed `GetStdHandle`, failed `GetConsoleMode`, failed `SetConsoleMode`, and
the success path; (2) `GOOS=windows go build ./...` and `GOOS=windows go vet
./...` both verified to compile cleanly, so the real `kernel32Console`
Win32-call wiring is at least type- and syntax-checked; (3) `enableConsoleANSI`
already fails closed (falls back to plain newline output, per
`cmd/agent-usage/main.go`'s `runWatch`) on any Win32 call failure, so a real
integration defect degrades to unstyled output rather than corrupting the
watch loop or crashing.

Accepting this as a residual, documented, non-blocking limitation rather than
a fix — actual native Windows execution of this path needs either a paid
runner tier or manual verification by someone on a Windows machine before
that platform's release build ships.
